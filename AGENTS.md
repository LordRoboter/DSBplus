# planner

## What This Repo Is
- Flutter app entrypoint is [lib/main.dart](lib/main.dart); it wires Firebase, provider state, notifications, and navigation.
- Core app state lives in [lib/services/data_repository.dart](lib/services/data_repository.dart) and [lib/services/plan_repository.dart](lib/services/plan_repository.dart).
- Shared theming is defined in [lib/theme.dart](lib/theme.dart); notification handling is isolated in [lib/services/notification_service.dart](lib/services/notification_service.dart).

## Working Conventions
- Use Flutter commands for day-to-day work: `flutter pub get`, `flutter analyze`, `flutter test`, and `flutter run`.
- Follow the existing Material 3 + provider pattern instead of introducing a new state-management or navigation approach.
- Keep logic in the service/repository layer when possible; avoid duplicating data-fetching or persistence behavior inside screens.
- Treat [analysis_options.yaml](analysis_options.yaml) as the lint baseline.

## Generated Files
- Do not hand-edit `build/`, platform-generated registrants, or other generated artifacts.
- `firebase_options.dart` is generated by FlutterFire; regenerate it instead of editing it manually.
- Splash/icon output is driven by [pubspec.yaml](pubspec.yaml); rerun the generator commands rather than editing generated assets.

## Asset And Packaging Notes
- When package dependencies change, update [pubspec.yaml](pubspec.yaml) and run `flutter pub get`.
- For launcher icons and splash screens, prefer the configured generators in [pubspec.yaml](pubspec.yaml) instead of patching platform output.
